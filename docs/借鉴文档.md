## 1. openpets — 近乎完整的答案 ★★★★★

**OpenPetsHQ/openpets** ｜ 1196★ ｜ TypeScript ｜ MIT ｜ 2026-09-15

> 本地优先的桌面伴侣平台，带动画宠物、插件 SDK 与编码助手集成。Electron 42 + React 19 + pnpm monorepo。

这是所有参考项目里**与 SuperPet 形态最接近**的一个，而且它的架构文档写得极清楚。**建议先通读它的 docs/ 再动手。**

### 1.1 看哪里

```
docs/architecture.md      # 一页式心智模型：三个运行时世界、包依赖脊梁
docs/plugins.md           # 插件平台：manifest 契约、权限模型、沙箱、安装、发布
docs/sdk.md               # 插件 SDK：ctx 命名空间与权限的对应表
docs/ipc.md               # 本地 IPC 协议：传输、发现握手、租约、安全边界
docs/pet-format.mdx       # 宠物包格式：reactions 映射、安装路径
docs/pets.md              # 渲染、反应、运动、安装
docs/mcp.mdx              # MCP 集成
docs/wayland.md           # Wayland 透明窗口的坑
plugins/official/openpets.reminders/   # 一个完整插件的样本
packages/mcp/src/         # MCP server 实现
packages/sdk/src/         # 类型契约 + 测试替身 + conformance check
```

### 1.2 抄什么

**① 「宿主拥有所有副作用，插件只描述意图」**
`docs/plugins.md` 的核心立场：插件从不直接往桌宠窗口注入 UI，只把描述符交给宿主，由宿主校验并渲染。这是插件安全的地基，SuperPet 的技能/能力包必须照做。

**② 权限四道防线**
`docs/plugins.md` 的权限模型：
- manifest 声明 → 用户安装时批准 → **每次 SDK 调用重新校验** → 配额限制
- 关键细节：**「陈旧授权永不授予当前 manifest 已不再声明的能力」**（交集语义）

**③ 插件 manifest 契约**
`plugins/official/openpets.reminders/openpets.plugin.json` 是可直接照抄的样本。要点：
- `manifestVersion` / `sdkVersion` 双版本号
- `permissions` 数组（`pet:speak`、`schedule`、`storage`…）
- `configSchema` —— **声明式配置，宿主自动渲染成设置表单**，插件不写 UI
- `assets` —— 图标必须打包进包内并 hash 固定，**禁止外链 SVG**

**④ manifest 读取要硬化**
`apps/desktop/src/plugin-manifest-reader.ts`：realpath 校验、允许根校验、manifest 必须是根文件、大小上限、id/version 匹配。**manifest 永不盲信**。

**⑤ 本地 IPC 协议**
`docs/ipc.md` + `apps/desktop/src/local-ipc*.ts`：
- 平台自适应传输（unix socket / named pipe / TCP）
- discovery 文件含 token，客户端要校验文件大小、权限、符号链接
- 行分隔 JSON、16KB 上限、超时 2s/3s
- 响应用 `ok` 判别联合类型
- **租约模型**（TTL 15s + 心跳）解决多方抢同一个桌宠窗口

**⑥ reactions 作为共同语言**
`docs/pet-format.mdx` + `apps/desktop/src/reaction-animation-mapping.ts`：调用方只说 `thinking` / `success` / `error`，由宠物包映射到具体动画，不支持则宿主回退。这套抽象让「动作包」可以自由增删。

**⑦ 其他可直接对号入座的模块**

| openpets 文件 | 对应 SuperPet 的什么 |
|---|---|
| `pet-window.ts` / `windows.ts` | 桌宠窗口管理 |
| `pet-motion-engine.ts` / `pet-roaming-controller.ts` | 动画/漫游引擎 |
| `mouse-forwarding.ts` | **窗口穿透模式**（点击穿透怎么实现） |
| `window-tracker.ts` / `window-occlusion.ts` | 跟随前台窗口、遮挡检测（决定是否降帧） |
| `plugin-sdk-quotas.ts` | 配额实现 |
| `pet-file-safety.ts` / `zip-safety.ts` | **文件与 zip 路径穿越防护**（必抄） |
| `confinement-manager.ts` | 限制模式（临时收敛权限） |
| `plugin-bubble-arbiter.ts` | 多来源气泡的仲裁（谁的话优先显示） |
| `voice-microphone-arbiter.ts` | 麦克风占用仲裁（防回声、防抢占） |
| `voice-privacy-indicator.ts` | 录音时的常驻隐私指示 |
| `plugin-ai-gateway.ts` | 插件用 AI 的统一网关（不让插件直连模型） |
| `lease-manager.ts` | 租约实现 |
| `packages/sdk/src/check-plugin-sdk.ts` | **契约漂移检测**：编译运行样例插件，发现三份契约不同步 |

**⑧ 契约三份拷贝规则**
`docs/sdk.md` 明说：发布的类型、宿主实现、测试替身是同一契约的三份拷贝，改一处必须同时改三处。SuperPet 的 PetPack / Skill / Pricing 三份契约都要立这条规矩。

**⑨ DESIGN.md**
`DESIGN.md` 是完整的 UI 设计系统手册（玻璃拟态、tactile 控件、色彩公式）。工坊 UI 的视觉方向可直接参考。

### 1.3 别学什么

- 它的产品核心是「桌宠反应编码 agent 的状态」，SuperPet 是「桌宠 + 语音助手」，产品逻辑不同，别照搬它的 agent 集成矩阵（那一堆 `@open-pets/claude`、`@open-pets/cursor` 包是它的业务，不是通用架构）。
- 它的 LAN 多桌宠模式（`lan-*.ts`）复杂度高，SuperPet 初期不需要。
- `wayland-*.ts` 是为了绕 Linux Wayland 的坑，SuperPet 若不做 Linux 可以先不看。

## 2. open-interpreter（codex-rs）— 执行安全边界 ★★★★★

**openinterpreter/openinterpreter** ｜ 68338★ ｜ Rust ｜ Apache-2.0 ｜ 2026-09-15

> 注意：这个仓库已重写为 Rust（`codex-rs`），是 Codex CLI 的 fork。**它从 Python 迁到 Rust 这件事本身就是对「执行层选 Rust」的投票。**

这是模块四（语音操控）最关键的参考——**不是看它怎么理解指令，而是看它怎么安全地执行指令。**

### 2.1 看哪里

```
codex-rs/execpolicy/README.md          # ★ 执行策略 DSL
codex-rs/execpolicy/src/{rule.rs,decision.rs,policy.rs,parser.rs,amend.rs}
codex-rs/sandboxing/src/{seatbelt.rs,landlock.rs,bwrap.rs,manager.rs,violation.rs,denial.rs,policy_transforms.rs}
codex-rs/linux-sandbox/  codex-rs/mxc-sandbox/
codex-rs/windows-sandbox-rs/  codex-rs/windows-sandbox-service/
codex-rs/exec-server/  codex-rs/code-mode/
```

### 2.2 抄什么

**① 执行策略 DSL —— 本仓库最值得抄的东西**

`execpolicy/README.md` 定义了一套规则语言：

```starlark
prefix_rule(
    pattern = ["cmd", ["alt1", "alt2"]],   # 有序 token，列表表示可选值
    decision = "prompt",                   # allow | prompt | forbidden，默认 allow
    justification = "解释规则为什么存在",     # ★ 会出现在审批提示里
    match = [["cmd", "alt1"], "cmd alt2"], # ★ 必须命中的样例
    not_match = [["cmd", "oops"]],         # ★ 必须不命中的样例
)
```

三个可直接搬走的点：
1. **`decision` 三态（allow / prompt / forbidden）就是风险分级的落地形态**——比抽象讨论「低/中/高」更可执行。
2. **`justification` 会展示在审批提示中**，这正好满足功能文档 §8.4「复述将要做什么」；`forbidden` 时还要求给出替代方案（例："Use `jj` instead of `git`"）。
3. **`match` / `not_match` 在加载期校验**，等于给策略规则配了单元测试。这是防止规则写错导致误放行的关键机制。

另外还有 `host_executable(name, paths)` 约束同名可执行文件的绝对路径解析，防「伪装的 git」。

**② 三平台沙箱实现**
`sandboxing/src/` 下是跨平台沙箱抽象：macOS 用 Seatbelt（`.sbpl` profile 文件：`seatbelt_base_policy.sbpl`、`seatbelt_network_policy.sbpl`）、Linux 用 Landlock + bubblewrap、Windows 用受限令牌/Job Object。`manager.rs` 是统一入口，`violation.rs` / `denial.rs` 定义违规与拒绝的表示。

SuperPet 的 `crates/executor` 沙箱层可以直接对标这个结构。

**③ 沙箱与策略的联动**
`policy_transforms.rs` —— 策略如何转换为沙箱参数。这条思路很重要：**策略决定"要不要做"，沙箱决定"最多能做到哪"**，两者是独立的防线，不能互相替代。

### 2.3 别学什么

- `codex-rs` 是一个巨型 workspace（几十个 crate），包含云端任务、ChatGPT 认证、代码模式等与 SuperPet 无关的东西，别被结构规模带跑。
- 它是**面向代码执行**的，SuperPet 面向的是文件/应用/系统设置操作，技能集完全不同。

## 3. leon — 技能声明式契约 ★★★★★

**leon-ai/leon** ｜ 17515★ ｜ TypeScript ｜ MIT ｜ 2026-09-15

> 开源个人助理，自带技能生态。

### 3.1 看哪里

```
skills/native/random_number_skill/          # 最简技能样本
  ├── skill.json        # ★ 声明
  ├── src/actions/run.py
  ├── locales/en.json
  ├── memory/
  └── test/
server/src/schemas/skill-schemas.ts         # ★ 技能的 zod schema
bridges/                                    # Python/Node 桥接
```

### 3.2 抄什么

**① 技能目录即契约**
每个技能是一个自包含目录：`skill.json`（声明）+ `src/actions/*`（实现）+ `locales/`（多语言）+ `memory/`（状态）+ `test/`。**新增技能 = 新增一个目录**，这正是 SuperPet「能力包/技能包可插拔」想要的形态。

**② skill.json 的声明结构**

```jsonc
{
  "$schema": "../../../schemas/skill-schemas/skill.json",
  "name": "Random Number",
  "bridge": "python",              // ★ 实现语言可换（python / node）
  "version": "1.0.0",
  "actions": {
    "run": {
      "type": "logic",             // ★ action 类型
      "description": "Generate and return a random number."
    }
  }
}
```

要点：**声明与实现分离**，`actions` 里只有类型和描述，实现放 `src/actions/<name>.py`。这让技能能被静态扫描、被 AI 路由、被 UI 渲染成命令面板。

**③ schema 用 zod 定义**
`server/src/schemas/skill-schemas.ts` —— 技能声明在代码层有强类型校验，同时能导出 JSON Schema。SuperPet 的 `packages/skill-protocol` 应对齐这个做法。

### 3.3 别学什么

- leon 的技能是「助手问答式」的（用户问，技能答），不是「操作电脑」的，所以它没有风险分级与沙箱——**这部分要去 open-interpreter 补**。
- `bridges/` 那套 Python 桥接正是 SuperPet 要避开的（见开发文档 §2.3）。

## 4. UFO — 多应用 GUI 操控编排 ★★★★

**microsoft/UFO** ｜ 9738★ ｜ Python ｜ MIT ｜ 2026-09-15

> UFO³，微软的 Windows 桌面 Agent。README 显示已支持 Windows / Linux / Mac / Android。

### 4.1 看哪里

```
ufo/agents/           # 智能体：states / processors / presenters / memory
ufo/automator/        # 动作执行
ufo/prompter/         # 提示词工程
ufo/rag/              # 经验检索
ufo/trajectory/       # 轨迹记录
ufo/experience/       # 经验沉淀
dataflow/             # UFO2：多应用工作流编排
  ├── execution/{agent,workflow}
  ├── schema/{execution_schema.json, instantiation_schema.json}
  └── instantiation/
galaxy/               # UFO3：星座式多设备协同
  ├── constellation/  session/  agents/  trajectory/  webui/
```

### 4.2 抄什么

**① 智能体状态机**
`ufo/agents/states/` + `processors/` + `presenters/` —— 把「感知 → 决策 → 执行 → 呈现」拆成独立处理器，用状态机串起来。SuperPet 的技能执行循环可参考这个分层，尤其是 **presenter 独立**这一点：执行结果如何呈现给用户，和怎么执行是两件事。

**② 工作流 schema 化**
`dataflow/schema/execution_schema.json` / `instantiation_schema.json` —— 多步任务被定义成可校验的 schema，而不是散落的代码。对应 SuperPet 功能文档 §8.6「多步任务按步骤展示进度」。

**③ 经验检索**
`ufo/rag/` + `ufo/experience/` + `ufo/trajectory/` —— 把执行轨迹沉淀成可检索经验。SuperPet 若要做「越用越懂你的桌面习惯」，这是参考起点。

**④ 平台已扩展到 MCP**
它的 README 显示 Linux/Mac 支持走 MCP server 形式，与开发文档选 MCP 作为技能协议一致。

### 4.3 别学什么

- 它的主战场是 Windows（UIAutomation 深度绑定），macOS 支持是后加的、较薄。
- 智能体复杂度高（多智能体 + 反思循环），SuperPet 初期只需要「单轮意图 → 技能」的直连路由，别过早引入多智能体。

## 5. ComfyUI — 生成流水线 ★★★★

**Comfy-Org/ComfyUI** ｜ 133419★ ｜ Python ｜ **GPL-3.0** ｜ 2026-09-16

### 5.1 看哪里

```
api_server/                          # HTTP API（供外部调用）
comfy/background_removal/            # ★ 抠图
  ├── birefnet.py
  └── birefnet.json
execution.py                         # 执行队列
comfy_execution/                     # 执行图引擎
custom_nodes/                        # 插件机制
folder_paths.py                      # 模型/资源路径管理
```

### 5.2 抄什么

**① 节点图作为生成流水线的表达**
SuperPet 的工坊生成链路「上传照片 → 抠图 → 风格化 → 动作生成 → 打包」在 ComfyUI 里天然就是一张节点图。**建议直接把 ComfyUI 当独立服务跑，客户端通过 `api_server` 提交任务**，而不是自己实现生成链路。

**② 抠图现成方案**
`comfy/background_removal/birefnet.py` —— BiRefNet 抠图，正是功能文档 §5.2「自动抠图、去背景」需要的。也可单独抽出来做 ONNX 本地推理。

**③ 执行队列与中断**
`execution.py` + `comfy_execution/` —— 任务队列、进度上报、中断。工坊「生成进度展示 + 可重试 + 失败不重复扣费」可参考。

**④ custom_nodes 插件机制**
生成能力的插件化方式，与 SuperPet 的能力包思路同构。

### 5.3 别学什么 / 注意

- **GPL-3.0**。作为独立服务走 HTTP 调用是常见做法，但**务必让法务确认**，不要把它的代码链接进闭源客户端。
- 它是重装备（Python + PyTorch + GPU），**绝不能打包进桌面客户端**。

## 6. PPet — 桌面透明窗口 ★★★★

**zenghongtu/PPet** ｜ 2032★ ｜ TypeScript ｜ MIT ｜ 2024-06-18

### 6.1 看哪里

```
src/main/index.ts        # ★ 透明窗口创建（options 从第 53 行起，transparent 在 58 行）
src/main/window.ts       # 窗口封装
src/main/tray.ts         # 托盘
src/main/initConfig.ts   # 配置初始化
src/renderer/src/models/ # Live2D 模型加载与切换
src/renderer/public/scripts/  # pixi + live2d core（本地内置，不走 CDN）
```

### 6.2 抄什么

**① 透明窗口的完整参数组合**（`src/main/index.ts`）

```js
{
  alwaysOnTop: true,        // 置顶
  transparent: true,        // 透明
  frame: false,             // 无边框
  hasShadow: false,         // 关阴影（否则透明区域有黑边）
  skipTaskbar: true,        // 不占任务栏
  resizable: false,
  minimizable: false,
  maximizable: false,
  webPreferences: {
    backgroundThrottling: false,   // ★ 关键：防止后台时动画被节流
    webSecurity: false,            // 加载本地 file:// 资源需要
  }
}
```

`hasShadow: false` 和 `backgroundThrottling: false` 是两个容易踩坑的点。

**② 渲染资源本地内置**
`src/renderer/public/scripts/` 里直接放了 `pixi.min.js`、`live2dcubismcore.min.js`、`live2d.min.js`、`live2dv3.min.js`——**Live2D Core 不能从 CDN 加载**（有域名白名单限制），必须打包进应用。

**③ 配置外置**
`src/common/paths.ts` / `src/common/config.ts` + `configs/` + `paths.json`——配置与路径不写死在代码里。

### 6.3 别学什么

- Electron 16 已过时，用新版（openpets 用 42）。
- `webSecurity: false` 是安全隐患，SuperPet 应改用自定义 protocol handler 加载本地资源，而不是全局关掉 webSecurity。
- 它没有做空闲降帧，24 小时挂机会耗电。

## 7. pixi-live2d-display — Live2D 渲染层 ★★★★

**guansss/pixi-live2d-display** ｜ 1505★ ｜ TypeScript ｜ MIT ｜ 2024-08-20

### 7.1 看哪里

```
src/Live2DModel.ts        # 模型主类
src/Live2DTransform.ts    # 变换/交互（拖拽、注视）
src/cubism2/  src/cubism4/  src/cubism-common/   # 两代 Cubism 适配
src/factory/              # 模型加载工厂
src/config.ts             # 全局配置（日志、音量等）
src/tools/                # 调试工具
```

### 7.2 抄什么

**① 双版本 Cubism 适配的抽象方式**
`cubism2` 与 `cubism4` 并存，通过 `cubism-common` 抽公共层。SuperPet 的 `pet-runtime` 要支持多种渲染后端（spritesheet / sequence / live2d），应学这种「共同接口 + 多实现」的结构。

**② Live2DTransform**

## 最后：三条最容易踩的坑

1. **Live2D 的商用授权独立于仓库 License**。pixi-live2d-display 是 MIT，但 Live2D Cubism SDK 有自己的许可协议，商用前必须单独确认。
2. **GPL-3.0 项目只能读思路**。`Ark-Pets`、`DyberPet`、`live2d-widget`、`ComfyUI` 都在此列。ComfyUI 走独立服务 HTTP 调用是常见规避方式，但仍需法务确认。
3. **别把 Python 带进客户端**。`my-neuro`、`UFO`、`autoMate`、`OmniParser`、`OpenVoice`、`ComfyUI` 都是 Python 项目，全部应作为**服务端或云端能力**，客户端只留 Electron + Rust + 少量原生二进制。
