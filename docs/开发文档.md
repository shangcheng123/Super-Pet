## 1. 范围与前提

本文覆盖「怎么做」，不重复「做什么」（见功能文档）。所有决策遵循两条硬约束：

1. **可扩展优先**：能力/技能/画风/动作都是声明式配置，新增不改主干代码。
2. **不写死**：价格、能力清单、技能白名单、模型供应商全部配置化。

## 2. 技术选型

### 2.1 结论总表

| 层 | 选型 | 备选（被否） | 决策理由 |
|---|---|---|---|
| 桌面外壳 | **Electron 42 + TypeScript** | Tauri、Flutter、Qt | Live2D 的 Cubism Web SDK 只有 Web 生态；透明窗口/置顶/穿透跨平台最成熟 |
| 桌宠渲染 | **PixiJS + pixi-live2d-display** | 自研 WebGL、Cocos | 现成 Live2D 渲染，动画状态机可自研 |
| 工坊/UI | **React 19 + Tailwind + zustand** | Vue、Svelte | 生态与参考实现一致 |
| 本地技能执行 | **Rust 独立进程** | Node 子进程、Python | 安全边界需单二进制 + 最小权限 + 易签名；`open-interpreter` 也已重写为 Rust |
| ASR | **whisper.cpp 二进制** | 云 ASR、Python 侧车 | 端侧、离线、无 Python 运行时 |
| TTS | **ONNX Runtime (Node)** | Python TTS、云 TTS | 留在 Node 进程内，避免打包 Python |
| 图像生成 | **云端 API / ComfyUI 独立服务** | 客户端内嵌模型 | 客户端不该背模型；ComfyUI 走 HTTP 也规避 GPL 传染 |
| 云端业务 | **Go** | Node/NestJS、Python | 计价需精确 decimal、并发、部署简单 |
| AI 网关 | **Go** | 直连供应商 | 屏蔽供应商，可切换可灰度 |
| 技能协议 | **MCP + 扩展注解** | 自研协议 | 复用生态；`ToolAnnotations` 天然映射风险等级 |
| 数据 | **Postgres + Redis + 对象存储** | — | 常规选择 |
| 包管理 | **pnpm workspace** | npm/yarn | 参考实现一致，monorepo 友好 |

### 2.2 为什么是 Electron 而不是 Tauri

诚实说明权衡：

- **Electron 的缺点**：常驻内存 200–300MB。桌宠 24 小时挂着，这是真实成本。
- **Tauri 的缺点**：Linux 透明窗口依赖 WebKitGTK，行为不稳定；Live2D 在 macOS WKWebView 上的表现缺乏生产验证。

选 Electron，但必须做三件事把成本压住：**单窗口、空闲降帧、离屏暂停渲染**。

同时**强制解耦**：渲染层与业务代码禁止直接调用 Electron API，全部走内部接口。这样将来换 Tauri 时只需替换外壳实现。

### 2.3 为什么客户端「零 Python」

参考项目 `my-neuro` 是 Python + 一批 `.bat`，Windows 专属、无法签名分发，是反面教材。Python 的打包（PyInstaller）与多二进制公证在 macOS 上代价很高。

替代方案：

| 能力 | 替代实现 |
|---|---|
| ASR | `whisper.cpp` 编译单二进制，子进程调用（`bindings/javascript` 可直连 Node） |
| TTS / 声音克隆 | `onnxruntime-node` 跑 ONNX 模型，进程内推理 |
| 图像生成 / 风格迁移 | 云端 API；本地则连 ComfyUI 独立服务（HTTP） |
| 抠图 | BiRefNet ONNX 本地跑，或走 ComfyUI |

Python 只出现在**服务端**做训练与实验，不进客户端。

### 2.4 为什么执行层单独用 Rust

技能执行是**唯一会碰用户文件和系统设置**的地方，是安全边界。独立进程 + 单二进制的好处：

- 崩溃不影响 UI 主进程
- 可单独施加沙箱（macOS seatbelt / Linux landlock+bwrap / Windows job object）
- 签名与公证简单（无运行时依赖）
- 最小权限可按技能粒度收敛

`open-interpreter` 重写为 `codex-rs` 后专门拆出 `execpolicy` / `sandboxing` / `linux-sandbox` / `windows-sandbox-rs` 等 crate，正是这条路线的生产验证。

**过渡策略**：团队若无 Rust 经验，第一阶段用 Node 子进程实现同样的接口，接口稳定后再换 Rust 实现。

## 3. 系统架构

### 3.1 进程拓扑

```
┌──────────────────────────────────────────────────────────────────┐
│ Electron 主进程 (Node)                                            │
│  · 状态机 / 窗口 / 托盘 / 桌宠窗口                                  │
│  · 本地 IPC Server（unix socket / named pipe）                     │
│  · 插件运行时 + 权限桥                                              │
│  · 云 API 客户端                                                   │
└───────┬───────────────────┬──────────────────┬───────────────────┘
        │ IPC (contextBridge)│ stdio JSON-RPC  │ HTTP/WS
        ▼                   ▼                  ▼
┌───────────────┐  ┌──────────────────┐  ┌──────────────────────┐
│ 渲染进程       │  │ executor (Rust)  │  │ 云端服务 (Go)         │
│ · PixiJS 桌宠  │  │ · 技能注册/路由   │  │ · api: 账户/订单/计价  │
│ · React UI     │  │ · 风险分级       │  │ · ai-gateway: 供应商   │
│ · 气泡/面板    │  │ · 沙箱执行       │  │ · 权益校验            │
│               │  │ · 审计/撤销      │  │                      │
└───────────────┘  └──────────────────┘  └──────────────────────┘
        ▲                                        ▲
        │ 子进程                                  │ 云 API
┌───────────────┐                        ┌──────────────────────┐
│ whisper.cpp   │                        │ ComfyUI (独立服务)     │
│ (ASR 二进制)   │                        │ 生成流水线             │
└───────────────┘                        └──────────────────────┘
```

### 3.2 分层职责与依赖方向

依赖只能自上而下，禁止反向：

| 层 | 职责 | 禁止 |
|---|---|---|
| UI 层 | 渲染、交互、展示 | 直接读写文件、直接调系统 API |
| 宿主层（主进程） | 状态、窗口、权限裁决、插件沙箱 | 直接执行系统命令 |
| 执行层（Rust） | 技能执行、沙箱、审计 | 承载业务逻辑 |
| 服务层（Go） | 账户、计价、订阅、AI 代理 | 依赖客户端实现细节 |

**核心原则：宿主拥有所有副作用，插件只描述意图。** 这条直接借自 openpets 的插件平台设计（见借鉴文档 §1.3）。

### 3.3 三条关键数据流

**A. 生成流（工坊）**
```
选形象/画风/动作/功能 → 客户端向服务端 POST /v1/quote（实时报价，仅展示）
→ 用户确认 → POST /v1/orders（服务端复算 + 扣点 + 返回 jobId）
→ 生成任务：抠图 → 风格化 → 动作生成 → 打包 PetPack
→ 客户端下载 PetPack → 校验 → 安装 → 桌面渲染
```

**B. 对话流**
```
用户输入（文字/语音）→ 唤醒判定 → ASR（本地 whisper.cpp）
→ 云端 LLM（带人设 + 上下文 + 能力清单）→ 若返回 tool_call 则转 C
→ TTS（本地 ONNX）→ 播放
```

**C. 语音操控流**
```
唤醒 → ASR → 意图理解（LLM + 技能路由）
→ 命中技能 → 参数校验 → 风险分级
   ├─ 低 → 直接执行
   ├─ 中 → 复述计划 + 单次确认
   └─ 高 → 影响清单 + 二次确认（可选确认词）
→ 执行（沙箱内）→ 结果播报 → 写审计日志 → 登记撤销点
```

## 5. 核心契约

契约是整个架构的地基，全部**版本化 + JSON Schema + 代码生成**。三份契约定义清楚后，各层可以并行开发。

### 5.1 PetPack manifest

产出物契约。所有形象/动作/人设/能力都装在这里。

```jsonc
{
  "petPackVersion": 1,
  "id": "pet_01HX...",
  "name": "咪咪",
  "createdAt": "2026-09-16T10:00:00Z",
  "appearance": {
    "kind": "spritesheet",          // spritesheet | sequence | live2d
    "assets": [
      { "ref": "appearance/main@2x.png", "scale": 2 }
    ],
    "canvas": { "width": 512, "height": 512 },
    "anchor": { "x": 0.5, "y": 1.0 }
  },
  "animations": [
    { "state": "idle",   "source": "animations/idle.json",  "loop": true,  "fps": 12 },
    { "state": "walk",   "source": "animations/walk.json",  "loop": true,  "fps": 12 },
    { "state": "happy",  "source": "animations/happy.json", "loop": false, "fps": 12 }
  ],
  "reactions": {                     // 反应 → 动画映射，缺失时回退
    "idle": "idle", "thinking": "idle", "success": "happy", "error": "sad"
  },
  "triggers": [                      // 动作触发条件，运行时可改
    { "animation": "walk",  "when": { "type": "interval", "everyMs": 60000 } },
    { "animation": "happy", "when": { "type": "event", "name": "pet.click" } }
  ],
  "persona": {
    "displayName": "咪咪",
    "promptRef": "persona/system.md",
    "voiceProfileId": null,          // 未购语音能力时为 null
    "locale": "zh-Hans"
  },
  "capabilities": [
    { "code": "chat.text", "quota": { "unit": "tokens", "limit": 100000 } }
  ],
  "license": { "type": "personal", "transferable": false }
}
```

**设计要点**
- `reactions` 是集成方/插件/桌宠之间的**共同语言**（借自 openpets）：调用方只说「思考/成功/失败」，由 PetPack 决定播哪个动画，不支持则回退。
- PetPack **只描述资源，不允许携带可执行代码**。这是防注入的关键。
- `kind` 支持三种渲染后端，新增后端只需加一种 `kind`。

### 5.2 技能描述符（MCP Tool + 风险注解）

技能 = MCP Tool 标准字段 + `x-superpet` 扩展。不破坏 MCP 兼容性，同时携带风险/撤销/沙箱信息。

```jsonc
{
  "name": "file.organize",
  "description": "把指定目录里的文件按类型或日期归类到子目录",
  "inputSchema": {
    "type": "object",
    "properties": {
      "directory": { "type": "string", "description": "绝对路径" },
      "by": { "type": "string", "enum": ["type", "month"] }
    },
    "required": ["directory", "by"],
    "additionalProperties": false
  },
  "annotations": {
    "title": "整理文件夹",
    "readOnlyHint": false,
    "destructiveHint": false,
    "idempotentHint": false,
    "openWorldHint": false
  },
  "x-superpet": {
    "riskLevel": "medium",                 // low | medium | high | forbidden
    "undo": { "strategy": "move-back", "ttlMs": 86400000 },
    "dryRun": true,                        // 支持先预览
    "scope": { "paths": ["~/Downloads", "~/Desktop", "~/Documents"] },
    "confirmTemplate": "将移动 {count} 个文件到子目录，其中 {detail}",
    "requiredPermissions": ["files:write"]
  }
}
```

**风险分级由 MCP 注解推导，也允许显式覆盖**：

| MCP 注解 | 推导风险 | 处理 |
|---|---|---|
| `readOnlyHint: true` | low | 直接执行 |
| 都未设置 | medium | 复述计划 + 单次确认 |
| `destructiveHint: true` | high | 影响清单 + 二次确认 |
| `openWorldHint: true` | medium→high | 对外发送，强制确认 |
| `x-superpet.riskLevel: "forbidden"` | forbidden | 禁止执行（仅策略可解禁） |

### 5.3 计价契约

**客户端只预估，服务端才结算。**

```
POST /v1/quote                 # 纯计算，不落单，可随时调用
{
  "items": [
    { "type": "base" },
    { "type": "style",      "code": "pixel" },
    { "type": "action_pack","codes": ["idle", "walk", "sleep"] },
    { "type": "capability", "code": "chat.text" },
    { "type": "capability", "code": "voice.tts" }
  ],
  "coupon": "FIRST10"
}
→ 200
{
  "quoteId": "q_01HX...",
  "currency": "CNY",
  "lines": [
    { "code": "base",       "label": "基础生成费",   "unitPrice": 9.9, "qty": 1, "amount": 9.9 },
    { "code": "pixel",      "label": "像素风",       "unitPrice": 0.0, "qty": 1, "amount": 0.0 },
    { "code": "idle,walk,sleep", "label": "动作包 ×3", "unitPrice": 2.0, "qty": 3, "amount": 6.0 },
    { "code": "chat.text",  "label": "文字对话",     "unitPrice": 4.0, "qty": 1, "amount": 4.0 },
    { "code": "voice.tts",  "label": "语音对话",     "unitPrice": 5.0, "qty": 1, "amount": 5.0 }
  ],
  "subtotal": 24.9,
  "discount": 0,
  "creditsApplied": 1200,
  "total": 24.9,
  "expiresAt": "2026-09-16T10:30:00Z"
}

POST /v1/orders                # 带 quoteId，服务端复算并比对
{ "quoteId": "q_01HX...", "idempotencyKey": "..." }
```

**硬性要求**
- 价格表后台配置化，客户端**不得**包含任何价格常量。
- 订单必须落「计价快照」（选了哪些项、单价、折扣、最终价），可复算可追溯。
- 金额用 decimal，禁止浮点。
- `quoteId` 过期或价格变动时，下单返回明确错误，让用户重新确认。

### 5.4 本地 IPC 协议

供外部集成（CLI、编辑器插件、第三方）驱动桌宠。设计直接借鉴 openpets 的 `docs/ipc.md`。

- **传输**：macOS/Linux 用 Unix domain socket，Windows 用 named pipe。
- **发现**：应用写 discovery 文件（含 endpoint + token），客户端读文件并校验（大小、权限、符号链接、Linux 下 `XDG_RUNTIME_DIR` 必须 `0700`）。
- **协议**：行分隔 JSON，`{ id, version, token, method, params }`；单条消息上限 16KB；连接超时 ~2s、响应 ~3s。
- **响应**：`{ ok: true, ... }` 或 `{ ok: false, error, code }`。
- **租约**：多集成方共享桌宠时用 lease（TTL 15s + 心跳），避免抢窗口。

```
hello | status | pets.list | pets.install | pet.react | pet.say | pet.showMedia
lease.acquire | lease.heartbeat | lease.release
```

## 6. 关键机制

### 6.1 桌宠渲染与动画状态机

- 渲染层独立为 `packages/pet-runtime`，**不依赖 Electron**，只接受 canvas 与资源，便于未来换外壳或做网页预览。
- 状态机支持优先级抢占：`交互 > 情绪 > 移动 > 待机`，新状态可打断低优先级状态。
- 空闲降帧：无交互且窗口不可见时降到 1–5 fps；`prefers-reduced-motion` 时保持首帧静态（无障碍）。

### 6.2 技能执行与风险分级

执行器流程：

```
收到 tool_call
  → 校验 inputSchema（类型/范围/长度/深度/大小上限）
  → 策略引擎裁决（allow | prompt | forbidden）
  → dry-run（若技能支持）生成影响清单
  → 按风险等级走确认
  → 沙箱内执行
  → 写审计日志 + 登记撤销点
  → 返回结构化结果
```

**策略引擎用规则 DSL**（借自 `codex-rs/execpolicy`）：

```starlark
# policies/default.rules
prefix_rule(
    pattern = ["rm", ["-rf", "-r"]],
    decision = "forbidden",
    justification = "删除请改用『移到回收站』技能 file.trash",
    match = [["rm", "-rf"], "rm -r"],
    not_match = [["rm", "report.txt"]],
)

prefix_rule(
    pattern = ["mv"],
    decision = "prompt",
    justification = "移动文件可能改变用户的目录结构",
)

prefix_rule(
    pattern = ["open", "-a"],
    decision = "allow",
    justification = "启动应用为低风险操作",
)
```

`match` / `not_match` 在加载时校验，相当于**规则自测**——这是这套设计最值得学的一点。

### 6.3 权限与沙箱

| 平台 | 沙箱方案 | 参考 |
|---|---|---|
| macOS | Seatbelt（`sandbox-exec` / SBPL profile） | `codex-rs/sandboxing/src/seatbelt.rs` |
| Linux | Landlock + bubblewrap | `codex-rs/sandboxing/src/landlock.rs`、`bwrap.rs` |
| Windows | Job Object + 受限令牌 | `codex-rs/windows-sandbox-rs` |

四道防线（借自 openpets 的 defense in depth）：
1. **声明**：技能在 manifest 声明所需权限
2. **批准**：用户安装时授权，持久化
3. **运行时校验**：每次调用都重新校验，**陈旧授权不生效**（当前 manifest 不再声明的权限一律拒绝）
4. **配额**：调用频率、数据大小、执行时长上限

默认目录沙箱：只允许 `~/Downloads`、`~/Desktop`、`~/Documents`，其他路径需显式加白。

### 6.4 计费

- 点数扣减必须**幂等**（`idempotencyKey`），生成失败要能原路退回。
- 生成任务失败重试**不重复扣费**：扣费与任务绑定，任务终态才结算。
- 订阅权益校验放在服务端，客户端只缓存展示态。

### 6.5 语音链路

- 唤醒：本地关键词检测（避免全量上云）。
- ASR：whisper.cpp 子进程，VAD 切分，支持流式。
- 打断（barge-in）：播放中检测到用户说话即停 TTS。
- 隐私：麦克风权限、是否上传云端必须明示，UI 上有常驻指示（借自 openpets 的 `voice-privacy-indicator`）。
- 播放与采集互斥，避免回声（openpets 用 `voice-microphone-arbiter` 解决，同一问题值得抄）。

## 7. 工程规范

### 7.1 契约一致性

借鉴 openpets 的「三份拷贝必须同步」规则：一份契约存在**三处**——发布的类型定义、宿主实现、测试替身。任何一处变更必须同时改三处，并有一个 conformance check 编译运行样例来检测漂移。

### 7.2 测试

| 层 | 手段 |
|---|---|
| 契约 | JSON Schema 校验 + conformance check |
| 技能 | 每个技能带 fixture 与 dry-run 快照测试 |
| 策略规则 | `match` / `not_match` 加载期自测 |
| 渲染 | 无 Electron 的 headless 渲染测试 |
| 计价 | 报价用例表 + 快照（防价格回归） |

### 7.3 构建与发布

- Electron 用 electron-builder；Rust 用 `cargo build --release` 交叉编译。
- macOS 需对 Electron、Rust 二进制、whisper.cpp 二进制**分别公证**，注意 `entitlements` 与 `hardened runtime`。
- 插件包走「打包 → 校验 → 签名 → 上传 CDN」流水线（参考 openpets 的 plugins:publish 流程），下载后校验 hash。

## 8. 路线图

### 阶段一：跑通（不做 Rust、不做 MCP）

- Electron + TS 单进程，桌宠能显示、能走、能被点。
- 工坊：上传照片 + 3 种画风 + 待机/走路/情绪 + 文字对话。
- 报价与下单全链路（服务端 Go 计价）。
- 技能用**声明式配置 + 平台脚本**（Node 子进程执行），不引 Rust。

**验收**：能生成一只桌宠、能对话、能正确扣费。

### 阶段二：隔离

- 技能执行抽成独立进程，接口定型。
- 引入 MCP 技能协议 + 风险注解 + 策略规则 DSL。
- 二次确认交互、审计日志、撤销点。
- 低风险技能：调音量、打开应用、截图。

**验收**：危险指令被拦截并给出可读的影响清单。

### 阶段三：硬化

- Rust 执行器 + 三平台沙箱。
- 语音对话全链路（本地 ASR/TTS）。
- 订阅与权益体系。

**验收**：沙箱逃逸测试通过，语音操控端到端可用。

### 阶段四：生态

- 插件/技能市场 + 开发者 SDK + 分成。
- 第三方 PetPack 导入导出。
