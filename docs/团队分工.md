# SuperPet 团队分工

> 团队规模：3 人，**全能型（前端 / 后端 / 客户端都能做），并且全部使用 AI 辅助编码**。
> 关联文档：[功能文档](./功能文档.md) ｜ [开发文档](./开发文档.md) ｜ [借鉴文档](./借鉴文档.md) ｜ 根 [AGENTS.md](../AGENTS.md)

---

## 1. 分工原则

### 1.1 按「纵切」分，不按「技术层」分

❌ 不这样分：一个人前端、一个人后端、一个人客户端。
理由：按层分会让每个需求都要三个人同时动，联调面最大；全能团队按层分是浪费。

✅ 这样分：每人一条**完整可交付的纵切**，从界面到服务端自己端到端打通。
理由：三人各自能跑通自己的线，不需要等别人；冲突面收敛到「契约」这一个点上。

### 1.2 用 AI 写代码后，每个人的第一交付物是「规格」

AI 让产出速度翻几倍，瓶颈从「敲代码」搬到了**规格质量**和 **review**。所以每个人的工作顺序是：

```
先写规格（契约 / 用例 / 兼容矩阵 / 验收标准）
  → 让 AI 按规格写实现
  → 人工复核关键逻辑
  → 跨线互审
  → 合并
```

**规格不清就动手，等于三个人各让 AI 发明一套接口。**

## 2. 三条纵切

| | 人A：桌宠本体线 | 人B：工坊生成线 | 人C：平台交易线 |
|---|---|---|---|
| 一句话 | 桌宠怎么活着 | 桌宠怎么被造出来 | 桌宠怎么收钱、怎么干活 |
| 覆盖功能模块 | 模块二 运行时 | 模块一 工坊 | 模块三 计费账户、模块四 语音操控（阶段二起） |
| 客户端 | `apps/desktop/src/main`、`packages/pet-runtime`、`packages/ipc-client` | `packages/workshop-ui`、`apps/desktop/src/renderer`（工坊部分）、`packages/petpack-schema` | `packages/pricing-sdk`、账户/订阅/设置页 |
| 服务端 | 无（纯本地） | 生成流水线：抠图 → 风格化 → 动作生成 → PetPack 打包（ComfyUI HTTP 对接） | `services/api`、`services/ai-gateway` |
| **先写的规格** | IPC 协议、状态机优先级规则、降帧策略 | 8 步流程兼容矩阵、PetPack 契约 | 计价用例表、幂等与退款规则 |
| 阶段二接什么 | 技能执行器 + MCP + 策略 DSL | 二次确认交互、影响清单 UI | 订阅权益校验、审计日志存储 |
| 阶段一验收 | 桌宠能显示、能走、能被点、能对话 | 一张照片能出 PetPack 并装到桌面 | 报价准、扣点幂等、失败不重复扣费 |
| 模块说明书 | [pet-runtime/AGENTS.md](../packages/pet-runtime/AGENTS.md) | [workshop-ui/AGENTS.md](../packages/workshop-ui/AGENTS.md) | [api/AGENTS.md](../services/api/AGENTS.md) |

### 依赖关系（只有两条硬依赖）

```
人C 的 /v1/quote  ──→  人B 的报价面板        （第一天必须给人B mock 版）
人B 的 PetPack    ──→  人A 的运行时消费      （契约先冻结，用假资源包并行）
```

其余全部解耦。

## 3. 起步阶段：骨架必须单人搭完

全能团队最大的浪费是**三个人都去搭地基**。所以头几天：

| 谁 | 独占任务（其他人不要碰） |
|---|---|
| 人A | pnpm workspace 骨架、tsconfig、eslint（含「`pet-runtime` 禁止 import electron」规则）、CI 骨架、`fixtures/` 假数据目录 |
| 人B | `petpack-schema` 契约 + 假 PetPack 资源包（人A 用来调渲染，人C 用来做存储） |
| 人C | 计价契约 + mock `/v1/quote` + 报价用例表与快照测试 |

这三件事并行不冲突，做完就**冻结契约**，之后所有改动走 conformance check。

> 人B、人C 在等人A 骨架期间，可以先读参考项目并起草契约（见 [参考项目索引](../references/参考项目索引.md) §6 阅读顺序）。

## 4. 跨切面责任（不指定 owner 就一定没人做）

| 事项 | Owner | 说明 |
|---|---|---|
| 契约守门 / conformance check | 人A | 架构性最强，且是 PetPack 消费方 |
| 构建发布、macOS 公证 | 人C | Electron / Rust / whisper.cpp 三个二进制分别公证，注意 entitlements 与 hardened runtime |
| 设计规范（`DESIGN.md` + design token） | 人B | 纵切分工后没人天然管视觉一致性，必须指定 |
| 计价正确性 | 人C | 全项目最不能出错的地方 |
| 根配置（`package.json`、CI、lint） | 人A | 防止三个人同时改根文件 |

## 5. 轮换制度

全能团队不该有单点。**每个阶段结束轮换一次 owner**：

| | 阶段一 | 阶段二 | 阶段三 |
|---|---|---|---|
| 桌宠本体线 | 人A | 人C | 人B |
| 工坊生成线 | 人B | 人A | 人C |
| 平台交易线 | 人C | 人B | 人A |

理由：阶段二的执行器/沙箱、阶段三的语音链路是项目里最容易出事的模块，让三个人各过一遍手。

**轮换的接手动作**：先读该模块的 `AGENTS.md` + 契约 + 测试，再让 AI 动手。轮换成本靠「文档 + 契约 + 测试」压下来，这也是契约先行如此重要的原因。

## 6. AI 协作约定

### 6.1 防「AI 各自发明接口」

- **契约物理上只有一份**：JSON Schema 是唯一真相，TS 类型与 Go struct 由它**代码生成**，禁止手写、禁止各模块自定义同名类型。
- 契约变更 = 改 Schema → 重新生成 → 三方 review。不允许「顺手把接口改一下」。

### 6.2 每个模块都要有 `AGENTS.md`

已建立：根 [AGENTS.md](../AGENTS.md) + 三条线各一份。新增模块（如 `crates/executor`、`services/ai-gateway`、`packages/skill-protocol`）时，**先写 `AGENTS.md` 再写代码**。

`AGENTS.md` 里必须包含：职责边界、硬性约束、AI 最容易写错的点、测试要求、参考项目与 License 红线。

### 6.3 完成的定义（DoD）

1. 带测试：契约带 conformance check；计价带报价用例表 + 快照；技能带 fixture 与 dry-run 快照
2. 跨线互审：A↔B↔C 两两互审，全能团队互审成本很低
3. lint / typecheck / test 全绿
4. 不违反根 `AGENTS.md` 的硬约束与反面清单

### 6.4 必须人工逐行审的地方（不得只信 AI）

- `services/api` 的金额计算：decimal、并发扣点、幂等键、计价快照
- `packages/pet-runtime` 的状态机抢占优先级
- `packages/workshop-ui` 的风格 × 形象 × 动作兼容矩阵
- 任何涉及用户文件系统或系统设置的调用

### 6.5 工作流

- **小 PR + 频繁合并**：AI 一次生成几百行，三人并行时冲突成本极高。约定每人每天至少合一次。
- **目录级 CODEOWNERS**：见 [.github/CODEOWNERS](../.github/CODEOWNERS)，含义是「谁的 AI 在改这个目录，谁负责」。

## 7. 风险清单

| 风险 | 表现 | 对策 |
|---|---|---|
| 风格分裂 | 三个人各自按习惯写，仓库像三个项目拼的 | 骨架期一次定死 lint / 格式化 / 目录约定，**靠 CI 卡，不靠自觉** |
| 契约漂移 | 「顺手改一下接口」，联调才发现 | Schema 唯一真相 + 代码生成 + conformance check |
| AI 幻觉接口 | 两个 AI 对同一接口的字段名不一致 | 契约进 AI 上下文（`AGENTS.md` 指向契约位置） |
| 体验不一致 | 工坊和运行时视觉对不上 | 指定设计规范 owner（人B），出 `DESIGN.md` + design token |
| 计费静默出错 | float 参与金额、并发重复扣点 | 人C 逐行审 + 用例表 + 快照测试 + 幂等测试 |
